# numerical.run — merging ReRun and Streamlab

Compiled 2026-08-28. Grounded in the actual source of both repos (`jeanclawd/rerun`
`host/dag.js`/`format.js`/`session-core.mjs`, `jeanclawd/streamlab`
`streamlab.m`/`host/engine.js`), not just their READMEs.

## The one-sentence pitch

ReRun's reactive notebook engine + Streamlab's widget library + a portable,
`.m`-compatible file format that carries UI as comments instead of syntax —
one project, two faces (notebook and app), built almost entirely out of code
that already exists in both repos.

## The tension that actually matters

ReRun and Streamlab aren't cosmetically similar — they run on **opposite
execution models**, and any "merge" pitch has to resolve this or it's not a
real proposal:

- **ReRun**: incremental. `dag.js` builds a dependency graph; editing a cell
  reruns *only* that cell and its transitive dependents (`descendantsOf`).
  Built for exploration — you pay for what changed.
- **Streamlab**: total. Every `sl_*` interaction reruns the **entire script**
  top-to-bottom (`resetSession` → execute → render), Streamlit's actual model.
  Simple, predictable, and it has to be this way in isolation — there's no
  cell graph to be incremental *about*.

**The resolution:** a full rerun is already a degenerate case of what ReRun
does today. `run-all` already executes `graph.order` — every cell, in
topological order. Give Streamlab's widgets to ReRun's engine and "rerun
everything" is just the DAG at its widest scope, not a second execution
model bolted on next to the first. Nothing new to build here — this is
ReRun's *existing* run-all path, pointed at a notebook whose cells happen to
contain `sl_*` calls. The nice side effect: a merged app reruns
*incrementally* by default, which is strictly less work than Streamlab's
current full-rerun-always behavior — merging makes existing Streamlab apps
faster, not just prettier.

## Streamlab's widgets are already not a language extension

This is worth being precise about, because it changes what's actually left
to design. Per `streamlab/README.md` §"How it works": `sl_slider`, `sl_button`,
etc. are **plain user-space MATLAB functions**, defined in one library file
(`streamlab.m`), that print a marker line to stdout
(`%%SL%%{...json...}`) which the host parses. No RunMat core changes, no
parser changes, no new syntax — `v = sl_slider('freq', 1, 8, 2, 0.5)` is a
completely ordinary function call. State survives reruns by being *baked
into the generated source* as a `jsondecode` literal
(`sl_state_()`, regenerated by the host every run) — a workaround for
`global` being broken in RunMat 0.6.1, documented in `runmat-lab`.

So "keep `sl_*` as an advanced mode" isn't a design problem, it's already
true today, for free — that library drops into a ReRun cell unmodified.
`v = sl_slider(...)` is exactly as legal in a `.rerun.m` cell as
`plot(x, y)` is. The design work is entirely on the *other* side: the
WYSIWYG layer that writes those calls for you.

## The notebook format

Two round-trippable serializations of one model — cells, the DAG, widget/
layout metadata, not a new binary format:

**`.rerun.m` (already exists, unchanged in spirit).** Plain MATLAB,
`%%`-sectioned, in dependency order — runs top-to-bottom in real MATLAB,
Octave, or `runmat` CLI with zero numerical.run awareness. Round-trip
metadata already rides in comments, Pluto.jl-style
(`format.js`'s own description): `%% ⟳ <cell-id>` headers, a
`% ⟳ page-order: …` footer. This is the whole trick, and it's already
built — it's how a plain-text file stays git-diffable one-hunk-per-cell
*and* carries structure MATLAB itself doesn't have a syntax for.

**A markdown serialization — `.nb.md`, and now there's a real spec to build
on.** [JEP #103, "Official support for Markdown-based notebooks"](https://github.com/jupyter/enhancement-proposals/pull/103)
(Thiéry/Purves/Lisin, opened 2023-03-01, still unmerged/open as of this
writing) proposes exactly this extension and a concrete syntax: an optional
YAML frontmatter header for notebook metadata; code cells as
` ```{jupyter.code-cell} ` fenced blocks (execution count and id in the
info-string, cell metadata via a YAML block, MyST-style `:key: value`
shorthand, or single-line JSON — all three, deliberately, so authors can
pick concise-and-editable vs. exhaustive-and-unobtrusive); outputs as
sibling `{jupyter.output output_type=...}` blocks, one JSON object per line
per MIME type for diff-friendliness; text is just the surrounding Markdown
flow, split into cells with a `+++` thematic break (borrowed from MyST).
Worth noting: the JEP's own Motivation section already lists MATLAB's
cell convention as prior art alongside VS Code/Spyder/PyCharm — the
`%%`-section idea `.rerun.m` builds on isn't an outside influence to this
proposal, it's already inside its frame of reference.

Given a real spec exists, `.nb.md` should **adopt JEP #103's syntax as-is**
rather than inventing a divergent one — that's the whole point of building
on prior art instead of gesturing at it. Concretely: `{jupyter.code-cell}`
for MATLAB code cells (with a `matlab` language hint per the JEP's advisory
prefix — `` ```matlab {jupyter.code-cell} ``), `+++` for cell breaks between
narrative Markdown, and numerical.run's own widget/layout data as ordinary
cell metadata inside the mechanism the JEP already defines (the shorthand
block), rather than a separate bespoke directive:

    ```matlab {jupyter.code-cell}
    :widget: {kind: sl_slider, bind: f, x: 120, y: 40, w: 220}

    f = sl_slider('frequency', 1, 8, 2, 0.5);
    ```

That keeps `.nb.md` a plain, spec-following Markdown Jupyter notebook to
any JEP-103-aware tool — numerical.run-specific data just rides in cell
metadata the same way `tags` or slide config would.

**`⟳` pragmas stay exactly as they are for `.m` — that half doesn't
change.** JEP #103 is a Markdown syntax; it has nothing to say about plain
`.m` files, and MATLAB comments can't carry a fenced-directive block
anyway. The two serializations solve the same problem in the idiom each
host format already supports, which is the right split, not a compromise.

**The pragma vocabulary extends, doesn't replace, what's there.** Today
`⟳` carries exactly two things: cell identity and page order. Widgets need
one more: presentation metadata code can't express (a slider's position on
a free-form canvas, if the WYSIWYG editor goes beyond Streamlit's linear
top-to-bottom layout; grouping into panels; a caption). Proposed shape,
same sigil, same "ignorable by anything that doesn't know about it" property
the existing pragmas already have:

```matlab
% ⟳ widget: id=w3 kind=sl_slider bind=f x=120 y=40 w=220
```

A plain MATLAB reader sees a comment. numerical.run's WYSIWYG layer sees a
widget's canvas position tied to the `f = sl_slider(...)` call two lines up
by id. Delete the comment, the code still runs — the format degrades
gracefully to "just Streamlab," which is the whole point.

## The WYSIWYG editor

Not a new code editor — a **panel that writes code into the existing cell
editor**, the same relationship Webflow has to the HTML it generates, or
Streamlit Cloud's (much thinner) drag-and-drop had to `st.*` calls:

1. A component palette (slider, button, selectbox, text, metric, figure
   placeholder — `streamlab`'s existing `sl_*` surface, nothing invented).
2. Drag one onto the canvas → numerical.run inserts
   `v = sl_slider('label', ...)` into the target cell (new cell if dropped
   on empty canvas) *and* a `% ⟳ widget:` pragma recording where you dropped
   it.
3. The canvas re-renders from the **same live RunMat session** ReRun's
   notebook view already runs — this isn't a separate preview engine, it's
   the existing `SessionRunner`/`runIds` pipeline pointed at a different
   renderer.
4. Power users ignore the palette entirely and type `sl_slider(...)` by
   hand — the pragma is optional; a widget with no `% ⟳ widget:` line just
   renders in Streamlit's default top-to-bottom flow, which is what happens
   today anyway.

## Two views, one file, one session

- **Notebook view** — what ReRun already renders: cells, the DAG status
  badges, the workspace panel. For building and debugging.
- **App view** — what Streamlab already renders: widgets and outputs in
  place, code hidden. For using.

Both read the same `.rerun.m`/`.nb.md` file, run in the same session, and a
single edit in notebook view is immediately live in app view — there's no
separate "publish" step converting one into the other, because they were
never two file formats to begin with, just two renderers over one document.
(Streamlab's own deployment mechanisms — the link-is-the-deployment
base64 encoding, the single-file `pack.mjs` bundler, the Jupyter `%%streamlab`
cell — apply to app view unchanged; nothing about them assumed Streamlab's
full-rerun model specifically.)

## What's actually new vs. what's reuse

Concretely, against the two existing repos:

| Piece | Status |
|---|---|
| Reactive DAG engine (`dag.js`) | reuse as-is |
| RunMat session runner (`session-core.mjs`) | reuse as-is |
| Notebook cell UI (`app.js`, minus pair-specific bits) | reuse as-is |
| `.rerun.m` format + `⟳` cell/page-order pragmas (`format.js`) | reuse as-is |
| One-way `.ipynb` export (`format.js`) | reuse as-is |
| `sl_*` widget library + marker protocol (`streamlab.m`, `engine.js`) | reuse as-is |
| Deployment mechanisms (link-encode, `pack.mjs`, Jupyter cell) | reuse, generalize past full-rerun assumption |
| `% ⟳ widget:` pragma vocabulary | **new** |
| Markdown serialization (`.nb.md`) | **new** |
| WYSIWYG palette/canvas | **new** |
| App view renderer (widgets-in-place, code hidden, backed by the DAG instead of full-rerun) | **new**, but small — mostly restyling `app.js`'s existing render path |

The honest read: most of the hard engineering (the DAG, the RunMat session
bridge, the MATLAB-compatible round-trip format, the widget protocol) is
**done**, in two separate repos, by two separate teams of one. numerical.run
is primarily an integration and format-design project, not a from-scratch
build.

## IP posture

Worth stating plainly since it's the reason this is designed the way it is,
not an afterthought: `.rerun.m` was never close to `.mlx` in the first
place. MATLAB's `%%`-sectioned plain-text cell convention is MathWorks'
own long-documented, open convention for basic cell-mode editing — not the
proprietary zipped-XML `.mlx` Live Script container. numerical.run doesn't
touch that binary format at all; it stays on the open, plain-text side
MathWorks itself publishes, the same place ReRun already lives. The widget
layer doesn't change that risk profile either — `sl_*` is user-space
functions and comment pragmas, not new MATLAB syntax, so there's nothing
resembling a Live Script reimplementation anywhere in this design. Same
trademark posture streamlab's README already states, worth carrying
forward verbatim: RunMat™ is Dystr, Inc.'s mark, MATLAB® is MathWorks',
numerical.run isn't affiliated with either.

## Inspirations, named honestly

- **marimo** — ReRun's own stated inspiration already (reactive Python
  notebooks, DAG-driven reruns). numerical.run inherits this at one remove.
- **Pluto.jl** — `format.js` already cites this by name for the
  comment-pragma round-trip trick; the widget pragma extends the same idea.
- **Jupyter** — the `.ipynb` export path exists today; `nbformat`-shaped
  thinking (cells, outputs, a JSON model underneath) is worth keeping as
  the *third* interop target even if it's not a primary format.
- **Streamlit** — Streamlab's entire API surface and "the script is the
  app" philosophy, taken directly.
- **Jupytext / MyST-NB / Quarto** — the actual prior art for "markdown
  ⇄ notebook, round-trips losslessly."
- **[JEP #103](https://github.com/jupyter/enhancement-proposals/pull/103)**
  — the specific, still-unmerged proposal for `.nb.md` itself. Not a
  vague direction to gesture at; a concrete syntax to adopt (see "The
  notebook format" above). Its own Motivation section already cites
  MATLAB's cell convention as prior art, which is a good sign this and
  `.rerun.m` are pointed the same way.

## Open questions worth resolving before writing code

- Widget *state* today is baked into generated source text per run
  (`sl_state_()`) because `global` doesn't work. Does the DAG's incremental
  rerun still need that, or does per-cell scoping make a cleaner state
  channel possible? Worth checking against current RunMat before assuming
  the workaround is still necessary.
- Does the markdown serialization need to be lossless in *both* directions
  from day one, or is `.m` the source of truth with markdown as an
  export-first, import-later target (lower risk to ship)?
- Free-form canvas position (`x`/`y` in the pragma) vs. Streamlit's
  linear top-to-bottom flow — does v1 need real 2D layout, or does
  "insertion order = display order" (what Streamlab already does) cover
  the WYSIWYG editor's first cut too?
